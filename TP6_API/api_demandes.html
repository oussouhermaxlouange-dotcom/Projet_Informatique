1. Objet

Implémentation de la création, de la lecture et de la validation d'une demande, avec contrôles côté serveur. Sur 14 cas exécutés contre MySQL 8.0.46 et l'API réelle, 14 sont conformes à l'attendu écrit avant le test. La base tp3_conventions est rechargée depuis le jeu d'essai TP3 avant chaque exécution.

6. Sécurité et cohérence

PointMise en œuvre
Mots de passepassword_verify contre un hash password_hash (bcrypt) ; message identique pour compte inconnu et mot de passe faux.
Sessionsession_regenerate_id(true) à chaque connexion réussie ; cookie HttpOnly, SameSite=Lax ; identifiant inconnu refusé (use_strict_mode).
AutorisationRôle contrôlé côté serveur à chaque requête ; un étudiant ne voit et ne traite que ses demandes (403 sinon).
SQLRequêtes préparées avec paramètres liés, émulation désactivée ; aucun SQL dans les contrôleurs.
TransactionStatut et historique dans une seule transaction ; rollback complet si une étape échoue (vérifié par un test dédié).
ErreursLe détail technique va dans le journal serveur ; le client reçoit un message neutre et un code cohérent (400, 401, 403, 404, 409, 422, 503).

7. Justification (preuve de travail)

Les six cas exigés ont été écrits avant exécution, puis joués sur une base rechargée. Toutes les réponses sont conformes. Le rollback est vérifié séparément par tests/test_domain.php : une exception provoquée après l'UPDATE laisse le statut et le motif inchangés. Le code de l'API reste dans TP4_Architecture/ (couches contrôleur, service, dépôt) ; les preuves et le script de rejeu sont regroupés dans TP6_API/.

Reproduire : mysql ... < TP3_Modele_donnees/001_schema.sql puis 002_seed.sql, puis cd TP6_API && ./tests_api.sh.
