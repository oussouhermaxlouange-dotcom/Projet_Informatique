1. Objet et méthode

Vérifier l'application par une matrice de tests et des contrôles de sécurité. Les 14 cas ont été écrits avant exécution : l'attendu et le code HTTP attendu sont des paramètres du script tests_securite.sh, qui recharge la base TP3, démarre l'API sur le port 8086 et compare le code obtenu à l'attendu. Deux cas relisent en plus le statut en base (refus sans motif, validation répétée) et un cas compare le nombre de lignes avant et après une création invalide. Résultat : 14 / 14 conformes.

4. Autorisation et injection

Étudiante B vers le dossier de A (T-05) : la session de B est valide et la demande 1 existe ; la réponse est pourtant 403 ACCES_REFUSE, sans corps utile. Le contrôle est fait dans DemandeService sur etudiant_utilisateur_id. Étudiante A qui tente de décider (T-08) : 403 ROLE_NON_AUTORISE ; le rôle est vérifié côté serveur à chaque requête, jamais à partir d'un paramètre client.

Chaîne « 1 OR 1=1 » (T-06, T-09, T-09b) : comme identifiant de route, elle est rejetée par ctype_digit() avant tout appel au dépôt (404) ; dans le champ e-mail, par FILTER_VALIDATE_EMAIL (422) ; dans le mot de passe, par l'échec de password_verify() (401). Aucun de ces chemins ne construit de SQL par concaténation : requêtes préparées avec PDO::ATTR_EMULATE_PREPARES = false.

CSRF retenu : cookie de session SameSite=Lax, API JSON sans CORS, et contrôle explicite de l'en-tête Origin sur POST, PATCH, PUT et DELETE (src/Support/Csrf.php). Une écriture venue d'un autre site reçoit 403 ORIGINE_REFUSEE avant le routeur. Un client sans navigateur (curl) n'envoie pas Origin : il reste soumis à l'authentification par session. Le jeton de session par formulaire n'a pas été ajouté pour ne pas modifier le contrat du TP6 ; il est consigné en dette technique.
