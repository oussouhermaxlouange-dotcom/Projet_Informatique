1. Objet

Relier une interface Web accessible à l'API des demandes. L'interface est servie par la même application que l'API, dans TP4_Architecture/public/ : même origine, donc même cookie de session, sans duplication ni configuration CORS. Six écrans couvrent deux rôles : l'étudiante dépose et suit ses conventions, le responsable recherche, filtre et instruit les dossiers avant de valider ou refuser avec motif. Toutes les écritures passent par fetch ; aucun rendu n'utilise innerHTML.

2. Parcours des deux rôles

RôleÉcransActions et échanges
Étudiante Connexion → Mes demandes → Nouvelle convention → Détail Saisir entreprise, intitulé et deux dates ; soumettre la convention ; lire le statut, la date de décision ou le motif de refus. Une convention SOUMISE part vers le responsable.
Responsable Connexion → Dossiers à traiter → Décision → Détail Rechercher et filtrer par statut ; valider, ou refuser avec un motif obligatoire ; la décision revient dans le détail de l'étudiante et reste conservée.

3. Formulaire accessible

PointMise en œuvre
Étiquettes liéesChaque champ a un label for=… et un id unique (email, mot-de-passe, entreprise, intitule, date-debut, date-fin, motif).
Aide et erreursaria-describedby relie le champ à son texte d'aide et à sa zone d'erreur ; aria-invalid=true sur le champ fautif.
Zone d'erreurZone globale role=alert + aria-live=assertive ; une zone id=erreur-… par champ.
Messages de réussiterole=status : annonce polie, sans interrompre la saisie.
DécisionÉcran dédié sans dialogue : un refus sans motif est bloqué, le message s'affiche sous la zone de texte et le focus y est placé.
ClavierLien d'évitement, focus-visible sur tous les contrôles, navigation par boutons entre les six écrans.
CouleurStatut écrit en toutes lettres ; la couleur ne fait que renforcer.
Structure et langueUn seul h1 par écran, sections h2, tableaux avec caption et th scope=col ; lang=fr, dates JJ/MM/AAAA.

Les formulaires portent novalidate : la validation est faite par le serveur et les messages affichés sont ceux de l'API, ce qui permet de montrer les erreurs 422 réelles plutôt que les bulles du navigateur.

4. Gestion lisible des erreurs

CodeDéclencheurAffichage pour l'utilisateur
400Corps JSON illisible« Le corps de la requête doit être un objet JSON valide. »
401Session absente ou expirée« Authentification requise. » puis retour à la connexion ; « E-mail ou mot de passe incorrect. » à la connexion
403Rôle ou propriétaire incorrect« Vous n'avez pas les droits pour cette action. »
404Convention inconnue« Cette ressource est introuvable. »
405Méthode non autorisée« Cette action n'est pas autorisée sur cette ressource. »
409Décision déjà prise« Cette décision n'est plus possible… »
422Validation serveurMessage global + message sous chaque champ concerné
500Panne interne« Une erreur interne est survenue. Réessayez dans un instant. »
503Base indisponibleBadge « Service indisponible » et message dans la zone d'état

assets/api.js traduit le statut et le corps JSON en titre + liste de détails ; le message du serveur est préféré quand il existe. Preuve : preuves/12_erreurs_400_401_500.png et 03_erreurs_422.png.

5. Rendu sécurisé avec textContent

Chaque valeur reçue de l'API est insérée dans un nœud créé par document.createElement puis affectée à textContent ; le fichier assets/rendu.js ne contient aucun innerHTML. Deux charges hostiles ont été envoyées : <img src=x onerror=…> et <script>document.body.dataset.xss=…</script>. Résultat mesuré sur /preuves/xss.html : attribut data-xss absent, 0 élément(s) img créé(s), 0 élément(s) script dans le tableau. Les balises apparaissent en texte dans le tableau de l'étudiante, l'écran de détail et les cartes du responsable. Détail : preuves/xss_verification.txt et DOM complet preuves/xss_dom.html.
